# Variational quantum circuit heads for RL policies: generalization with few training layouts

Code, data and report of a master's thesis in AI. A reinforcement-learning policy (A2C, partially observable grid
navigation) whose output head is a variational quantum circuit with Born-rule readout (the action is the outcome of a
measurement) is compared with classical heads of the same size, in the regime of **few fixed training layouts**.

Main results (10 seeds per cell, test return on 100 unseen layouts, paired differences with 95% CI):

- With K = 25 training layouts the VQC head J (117 parameters) beats an MLP of the same size even when the MLP is
  brought to J's entropy: +2.13 [0.82, 3.44].
- A classical head with Fourier features (120 parameters) matches J: the advantage comes from the inductive bias of
  repeated data re-uploading, not from the circuit itself.
- With the noise of IBM Torino and Brisbane (calibrated Aer simulation, 1 shot per step) J loses 0.10 and 0.38 of return.

The full account, with tables and limits, is the report: [`docs/report_testa_vqc.md`](docs/report_testa_vqc.md) (in
Italian).

## Quick start

Python 3.13.

```
make setup      # virtual environment + pinned requirements
make test       # unit tests (Qiskit equivalence of the circuits included) + repository checks
make figures    # docs/figures/partA_curve_k.png and partB_noise.png
make tables     # results/tables_4_7.txt and tables_11_12.txt: tables 4-7 and 11-12 of the report
```

`make figures` and `make tables` read the round logs in `data/logs/` and the Part B results in
`quantum_heads/analysis/runs/noise/`, both in the repository; they take seconds. The trained weights and the raw data of
the distillation analyses are not distributed: to repeat the analyses that need them, retrain the runs (see
[`docs/REPRODUCE.md`](docs/REPRODUCE.md)) or ask the author.

## What is reproducible, and how exactly

1. **Figures and tables of the report.** From the shipped logs and results: both figures, tables 4-7 (curve in K,
   entropy control, paired differences, overfitting) and tables 11-12 (noise); the output matches the report. Table 8
   (greedy return), table 9 and 10 (policy distance, cross-distillation) need the trained weights, which are not distributed (retrain the runs or ask the author); see
   `docs/REPRODUCE.md`.
2. **Entropy-target sweep.** The 80 runs of the sweep of the thesis (MLP h5 and h128 at K=25, four entropy targets, 10
   seeds) are in `data/logs/ent-sweep-*`; `python scripts/summarize_entropy_sweep.py --logs data/logs` rebuilds the table
   and the figure. Their commands are generated by `scripts/sweep_entropy.py` (see `docs/REPRODUCE.md`).
3. **Retraining** is documented in [`docs/REPRODUCE.md`](docs/REPRODUCE.md): exact commands, seeds, the outer-step
   schedule. One run is bit-identical to the original only on the machine that produced it; on other hardware
   trajectories diverge after a few rounds. The check done so far (one seed, same machine, all 50 rounds) and its limits
   are written in that file.

## Layout

```
rl_env/          the environment (gymnasium), its specification and tests
rl_train/        A2C trainer, outer step, evaluation, round log, config
encoder/         shared encoder (perception, navigator, memory)
classic_heads/   MLP, shared linear head, Fourier head
vqc_core/        statevector and density-matrix simulators, noise channels
quantum_heads/   VQC heads I, J, K, their Qiskit reference circuits and tests
  analysis/      distillation, policy-equivalence and cross-distillation scripts; runs/ holds their results
scripts/         tables, figures, noisy evaluation (effective model and full Aer)
data/logs/       round logs of the runs of the report
docs/            report, design documents (docs/design), figures
thesis.pdf       the thesis (PDF/A-2b, in Italian); its LaTeX sources are not published
train.py         entry point of a training run
```

## Design documents

`docs/design/` holds the work plan and the specifications written before each experiment (hypotheses, design and
decision criteria fixed in advance). They are dated working documents: they refer to the tool that orchestrated the
original runs (a distributed-training runner, not part of this repository) and to commands as they were at the time.
`train.py` reproduces the training schedule of those runs on a single machine.
